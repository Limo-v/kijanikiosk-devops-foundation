# Week 8 Delivery Comparison for Nia

This week changes the release process from a server-by-server replacement routine into a packaged delivery flow. Last week proved that traffic could move between two standing environments and move back quickly when the new version failed. That was a meaningful control because it reduced exposure during a bad release. This week adds a stronger foundation underneath that control. The application is now packaged into a smaller production image, stored in a private registry with a traceable version tag, and scheduled onto a cluster that keeps the requested number of copies running.

Two numbers matter immediately. First, the production image dropped from 188MB in the Monday baseline to 94.2MB in the Tuesday production build, a reduction of 93.8MB. That matters because smaller artefacts move faster, start faster, and reduce the surface area carried into production. Second, the Thursday self-healing rerun replaced a deleted application instance in 19 seconds while service remained available through the remaining instance. That is not a theoretical advantage. It is measured recovery time from this week's evidence.

The most important difference is where trust now sits. In Week 7, trust sat in a specific server layout that had to be maintained correctly: two named environments, a traffic switch, state files, and a rollback script. In Week 8, trust moves into repeatable artefacts. The image contains the application in a form that can be rebuilt the same way, the registry holds the exact tagged version that should run, and the cluster compares desired state to actual state continuously. That means the operating model is less dependent on one machine staying in a carefully prepared condition.

| Concern | Week 7 | Week 8 |
|---|---|---|
| Deployment mechanism | Blue/green services on a single server, switched by `switch-env.sh` and nginx upstream changes. | Immutable container image `ghcr.io/limo-v/kk-payments:1.0.0-2a2d1b1` applied through a Kubernetes `Deployment` with two replicas. |
| Rollback mechanism | Monitor script detects failures and calls `rollback.sh` to move proxy traffic back to blue. | Primary protection is self-healing replacement by the controller; rollback becomes redeploying a known image tag or updating the `Deployment` to a previous tag. |
| Failure recovery | Recovery depends on the standby environment already being healthy and the proxy switch succeeding. | Recovery begins automatically when a Pod disappears; the controller schedules a replacement and the Service continues routing to the surviving Pod. |
| Scaling | Capacity change requires manually adding more server processes or more hosts outside the deployment workflow. | Replica count is part of the workload definition, so increasing copies is a declarative change rather than a separate server exercise. |

From a board perspective, Week 7 answered the question, "Can we move customer traffic away from a bad release quickly?" Week 8 answers a different question: "Can we rebuild and re-place the service in a standard way without depending on one handcrafted host?" That distinction matters. Last week reduced failure blast radius during release events. This week improves repeatability, portability, and operational consistency. A release is no longer just a script running on the correct server in the correct order. It is a versioned package, stored privately, pulled with controlled credentials, and started from a declared target state.

This also changes the credibility of traceability. The semver-SHA tag ties the running version back to a precise source snapshot. That gives a clean link between what was reviewed, what was pushed, and what was deployed. In the Week 7 model, version traceability was present but still depended heavily on local server state and hand-managed sequencing. In the Week 8 model, the same tagged artefact is the thing that gets promoted. That is a stronger basis for audit, repeat deployment, and controlled rollback because the release unit is more clearly defined.

Operationally, the self-healing measurement is the clearest sign of progress. A deleted instance was replaced in 19 seconds, and the service kept responding because another healthy copy stayed available. Week 7 could recover quickly from a bad release, but it did so by moving traffic between two prepared targets. Week 8 adds resilience during normal runtime, not only during planned deployment activity. That is the practical value Nia can present: the platform now helps absorb ordinary instance loss without turning every disruption into a manual incident.

Week 8 does not yet solve configuration separation, secret rotation inside the workload, or production-grade traffic safety during startup. Some values are still hardcoded, and health alone is not the same as readiness under real payment load. Week 9 adds dedicated configuration objects and secret management so environment-specific values can move out of the workload definition, reducing risk when the same application is promoted across multiple environments.
